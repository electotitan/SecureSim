Known limitations and decisions

No frontend yet: the frontend is unchanged. The spec schedules visualizations for Checkpoint 15, so the Huffman tree and byte grid aren’t drawn yet. The API already returns the data they need (tree, symbols, bytes).
Code table cost: the encoded bit length does not include sending the code table, and the API says so explicitly (table_overhead_included: false). For short texts, real Huffman output can exceed plain UTF-8 once the table is counted.
Single-symbol input: a text with one distinct symbol gets the code "0", giving efficiency 0% (entropy 0, length 1). This is a documented convention, not a mathematical result.
Surrogate check: the surrogate check in models.py is redundant in this Pydantic version, because pydantic-core already rejects lone surrogates. I kept it as defense in depth, labeled that in a code comment, and tested it directly.
Body-size limit: the 1 MB limit relies on the declared Content-Length. Chunked uploads without a length bypass it, but the 10,000-character field limit still applies.
Text-length cap: 10,000 characters is my choice, since the spec only says “sensible limits”. Tell me if you want it changed.

Known limitations

Greedy parsing: it is not optimal parsing, so an optimal parse could produce fewer tokens.
Measured comparison: the numbers in the docs come from a single seeded run (seed 1). They show that Huffman is stuck at 1 bit/char on a low-entropy source (H = 0.466) and that LZ77 expands structureless random text (ratio 0.79). They are observations and not general laws.
Response size: the API returns at most 2,000 token records (about 0.5 MB), while the statistics cover all tokens. tokens_truncated tells you when this applies.
Parameters: window_size and lookahead_size must be agreed out of band, since the serialized form doesn’t store them.
Size limits: the 40,000-byte input limit and the 32768/255 parameter caps are my choices, because the spec only says “sensible”.

Known limitations

AES-128 only: AES-192/256 return a proper 501 and are not silently downgraded. The spec’s pipeline signature mentions aes_key_bits, so the orchestrator will accept 128 only and say so.
Educational only: it is not constant-time and CBC has no integrity. Padding errors are distinguishable, which is a padding-oracle risk. This is stated in the code, the docs and every response (warning).
Seeded keys: seeded keys use random.Random. They are reproducible for experiments and insecure.
Response bounds: the API returns at most 64 per-block records (the ciphertext is always complete). The trace covers one chosen block.
Size cap: the 40,000-byte limit is my choice.
Equivalent mutant: one of the 95 mutants (pad length 0) is behaviorally equivalent, because the check was redundant. I pinned the specific error message instead.
Quick correction on my audit line: the “1 files mention pow(” line above is just gf_pow( in the field module, which is GF exponentiation and not Python’s pow. The restriction on Python’s three-argument pow() applies to RSA, and no file uses it.

Known limitations

Textbook RSA: it has no OAEP (deterministic, malleable), and every response says so. OAEP would need a hash and mask function from first principles.
Insecure keys: all keys are insecure, even the 160-bit ones. Seeded keys use random.Random and are reproducible, not secure.
Probabilistic primality: above 3.3×10²⁴ the test is probabilistic, with error below 4⁻²⁰ per composite.
Caps: modulus 12–512 bits in the API (1024 in the library) and p, q up to 256 bits. These are my choices.
What is returned: d, p, q and φ are returned because showing them is the point of the demonstration. A supplied AES key appears in the traces as an integer unless include_traces: false.

Known limitations

No message ID: the format has none, because the spec lists only sequence, total, payload and checksum. Two messages with the same total and non-overlapping sequences could therefore be mixed without detection. Only conflicting duplicates and mismatched totals are caught.
Weak header checksum: it is only the first layer. Payload integrity and reordering detection come from CRC-32 next.
Experiment scope: packet-level loss and corruption only. The bit-level channel comes in Checkpoint 10.
Seeded randomness: seeded loss and shuffling use random.Random, which is reproducible and not secure.
API caps: payload_size ≤ 4096 and data ≤ 40,000 bytes (the module allows 65,535-byte payloads), 256 table rows and 128 preview bytes per packet. These are my choices.
